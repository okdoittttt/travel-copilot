# Travel Copilot 보안 학습 로드맵 (12개월)

> 목표: 전문 화이트 해커가 아니라 **"보안을 아는 백엔드/AI 개발자"** 되기
> 배경: 금융기관 SI 프로젝트 투입 대비, 커리어 경쟁력 강화
> 방식: 실제 배포할 서비스 **Travel Copilot**을 만들면서, 개발 단계마다 해당 보안 주제를 같이 학습·적용한다
> 기준: 주 4~6시간, 12개월 (밀려도 괜찮음 — 단계 순서만 지키기)

## 진행 원칙

- **처음부터 안전하게 만든다.** 실제 운영할 서비스라서 "일부러 취약한 버전"은 만들지 않는다. 대신 공격 시나리오를 테스트로 작성해서, 방어 코드를 빼면 테스트가 실패하는지 확인하는 방식으로 학습한다
- **개발 순서를 따라간다.** 0~4단계는 MVP 12주 일정([../docs/02-mvp.md](../docs/02-mvp.md))과 맞물려 진행한다
- **점검 에이전트와 같이 간다.** 기능 하나를 끝낼 때마다 security/ 에이전트로 점검하고, 결과는 `security/reviews/`에 남긴다
- **실습은 내 환경에서만.** 점검·공격 도구는 로컬·스테이징에만 쓴다. 운영 환경 점검은 따로 확인한 뒤에 한다. 회사망·고객사망에서는 어떤 점검 도구도 실행하지 않는다

**스택**: Flutter (앱), FastAPI + PostgreSQL (서버), S3 호환 스토리지, Nginx, Docker Compose, GitHub Actions

## 0단계 — 기반 + 위협 모델 (1개월 / MVP 1~2주)

**목표**: 만들기 전에 무엇을 지켜야 하는지 정하고, 안전한 개발 환경을 갖춘다.

- [x] 위협 모델 초안 작성 (`security/threat-model.md`) — 자산 / 공격자 / 진입점 / 위협. 이후 단계마다 갱신
- [x] Docker Compose로 서버 + PostgreSQL + Nginx 구성 (파일 저장소는 F7)
- [x] 로컬 인증서(mkcert 등)로 Nginx에 TLS 적용
- [ ] Wireshark로 TLS 적용 전/후 내 트래픽 비교 캡처 (로컬에서만)
- [ ] Nginx ↔ 서버 내부 구간이 평문인지 확인하고, 운영에서 이게 문제가 되는 조건 정리
- [ ] TLS 핸드셰이크, 인증서 체인 흐름을 내 말로 정리 (`security/notes/tls.md`)
- [x] 비밀값은 처음부터 코드 밖으로: `.env` + `.env.example`, `.gitignore` 확인
- [x] gitleaks를 pre-commit 훅으로 걸어 비밀값 커밋 차단

**결과물**: `security/threat-model.md`(초안), `security/notes/tls.md`, TLS 적용된 로컬 환경

## 1단계 — 인증 (1~2개월 / MVP 3~4주)

**목표**: 소셜 로그인을 "되기만 하는" 수준이 아니라 안전하게 구현한다.

### 소셜 로그인 (카카오 · Apple · Google)
- [ ] OIDC 흐름 정리: ID 토큰이 무엇이고 서버가 왜 다시 검증해야 하는지 (`security/notes/oidc.md`)
- [x] ID 토큰 검증: 서명(JWKS), 발급자(iss), 대상(aud — 내 앱용 토큰인지), 만료(exp), nonce
- [x] 다른 앱용으로 발급된 토큰을 넣었을 때 거절되는지 테스트 작성
- [x] 사용자 식별은 `(provider, sub)` 조합으로. **이메일만 같다고 계정을 자동으로 합치지 않는다** (계정 탈취 경로)
- [ ] 카카오 · Apple · Google의 차이 정리 (Apple 이메일 숨기기, 카카오 이메일 미인증 가능성 등)

### 자체 토큰
- [x] 세션 vs JWT 트레이드오프 정리하고 선택 근거 기록 (docs/features/auth.md 5.4)
- [x] 액세스 토큰은 짧게(15분 안팎), 리프레시 토큰은 쓸 때마다 새로 발급(rotation)
- [x] 이미 쓴 리프레시 토큰이 다시 들어오면 탈취로 보고 해당 토큰 묶음 전체 폐기
- [ ] 로그아웃 · 회원 탈퇴 시 서버에서 토큰 폐기 — 로그아웃 완료(F1), 회원 탈퇴는 F9
- [x] 앱에서는 토큰을 flutter_secure_storage(Keychain/Keystore)에만 저장
- [x] 로그인·토큰 갱신 API에 요청 횟수 제한(rate limiting)

**결과물**: `docs/features/auth.md` (인증 설계 포함) + 구현, `security/notes/oidc.md`

## 2단계 — 인가 + 시큐어코딩 (2~3개월 / MVP 5~9주)

**목표**: "남의 여행"에 접근할 수 있는 길을 모두 막고, 공인된 보안약점 기준으로 코드를 점검한다.

### 인가 (여행 멤버 · 권한)
- [x] 모든 여행·일정·바우처 API에서 "요청자가 이 여행의 멤버인가, 권한은 무엇인가"를 확인하는 공통 의존성 구현
- [x] 보기 전용 멤버가 수정 API를 호출하면 거절되는지 확인
- [x] 내보낸 멤버가 이전에 받은 ID로 다시 접근하면 거절되는지 확인
- [x] 남의 여행 ID로 접근하는 IDOR 공격 테스트 (`server/tests/security/`)
- [x] 권한 체크를 빼면 위 테스트가 실패하는지 직접 확인

### 초대 링크
- [ ] 추측 불가능한 랜덤 토큰 (128비트 이상), DB에는 해시만 저장
- [ ] 만료 시각, 사용 횟수 제한, 폐기 기능
- [ ] 단톡방에 링크가 퍼졌을 때 피해 범위 정리 → 편집 권한 링크의 기본값 결정
- [ ] 딥링크는 커스텀 스킴이 아니라 Universal Links / App Links로 (다른 앱의 링크 가로채기 방지)
- [ ] 사용 횟수 제한을 동시 요청으로 우회할 수 있는지 테스트 (race condition)

### 시큐어코딩
**기준 자료**: KISA/행정안전부 「소프트웨어 개발보안 가이드」(보안약점 항목) — 금융 SI 납품 전 소스코드 진단에서 많이 쓰는 기준
**보조 자료**: OWASP Top 10, OWASP ASVS

- [ ] 보안약점 분류 체계(입력데이터 검증, 보안기능, 에러처리, 코드오류, 캡슐화, API 오용) 훑어보기
- [ ] 항목별 "내 코드 해당 여부 → 수정 방법 → OWASP 대응 항목" 대응표 (`security/secure-coding-checklist.md`)
- [ ] 입력값 검증: Pydantic 스키마로 타입·길이·범위 제한
- [ ] DB 접근은 ORM/파라미터 바인딩으로만
- [ ] 에러 응답에서 스택 트레이스·내부 정보 노출 제거 (전역 예외 핸들러)
- [ ] 동시 수정 충돌: `version` 컬럼으로 덮어쓰기 방지, 충돌 시 409

### 외부 API (Google Places · Routes)
- [ ] API 키는 서버에만, 앱은 서버를 거쳐 호출
- [ ] 사용자별 호출 횟수 제한 + Google Cloud 예산 알림·할당량 상한 (요금 폭탄 방지)
- [ ] 지도 표시용 키는 앱 번들 ID로 사용 범위 제한
- [ ] Google 응답도 외부 입력으로 취급 (그대로 저장·표시하기 전에 검증)

**결과물**: `security/secure-coding-checklist.md`, `server/tests/security/`

## 3단계 — 파일·암호화·모바일 (3개월 / MVP 10~12주)

**목표**: 여권 정보가 담긴 바우처를 서버에서도, 폰에서도 안전하게 보관한다.

### 파일 업로드
- [ ] 크기 제한, 확장자가 아니라 실제 파일 시그니처로 형식 판별 (PDF · JPEG · PNG만)
- [ ] 저장 파일 이름은 서버가 랜덤 생성, 원래 파일 이름은 따로 저장
- [ ] 서버는 업로드된 파일을 해석·렌더링하지 않는다 (PDF 파서 취약점 노출 줄이기)

### 서버 저장
- [ ] 해시 vs 암호화 차이, 대칭키 암호화 방식(AES-GCM) 정리
- [ ] 버킷은 비공개, 다운로드는 권한 확인 후 짧게 만료되는 URL(presigned URL)로만
- [ ] 저장 시 암호화 (스토리지 기본 암호화 vs 앱 레벨 봉투 암호화 비교하고 선택)
- [ ] 키를 코드 밖으로: 환경 변수 → KMS/볼트 개념 이해

### 기기 저장 (Flutter)
**기준 자료**: OWASP MASVS / Mobile Top 10
- [ ] 바우처 캐시는 앱 전용 폴더에 AES-GCM으로 암호화, 키는 Keychain/Keystore에
- [ ] 로그아웃 · 탈퇴 · 여행에서 내보내짐 → 기기 캐시 삭제
- [ ] 기기 백업(iCloud/Google)에 바우처가 들어가지 않게 설정
- [ ] 앱 로그(print/debugPrint)에 토큰·개인정보가 찍히지 않는지 확인
- [ ] 릴리스 빌드에서 API 키·비밀값이 들어 있는지 직접 추출해서 확인 (MobSF 등, 내 빌드만)
- [ ] 인증서 고정(pinning) 도입 여부 검토하고 결정 근거 기록

**결과물**: `docs/features/vouchers.md`, `docs/features/vouchers-offline.md` (저장·암호화 설계 포함) + 구현

## 4단계 — 자동 점검 파이프라인 (2~3개월, 0~3단계와 병행)

**목표**: 사람이 놓치는 문제를 도구가 잡게 하고, 결과를 판단하는 연습을 한다.

- [ ] GitHub Actions 워크플로 구성
- [ ] gitleaks (비밀값 유출 탐지)
- [ ] Semgrep (정적 분석), Bandit (Python 보안 린터)
- [ ] pip-audit (Python 의존성), osv-scanner (Dart/Flutter 의존성 포함)
- [ ] Trivy (컨테이너 이미지·설정)
- [x] Dockerfile 점검: root가 아닌 사용자로 실행, 최소 베이스 이미지
- [ ] OWASP ZAP baseline 스캔을 **로컬에서 띄운 내 서버에만** 실행
- [ ] 경고마다 진짜 문제인지 오탐인지 판단하고 근거 기록 (`security/scan-triage.md`)

> 실무 포인트: 프로젝트에서 진단 도구 결과에 대해 "조치 완료 / 오탐 소명"을 요구받는 일이 많다. 그 연습이다.

**결과물**: `.github/workflows/security.yml`, `security/scan-triage.md`

## 5단계 — 배포·운영 보안 (4~5개월)

**목표**: 운영 환경을 로컬보다 느슨하게 만들지 않는다.

- [ ] 호스팅 선택 (AWS / GCP / Fly.io 등)과 보안 관점 비교
- [ ] 운영 TLS (Let's Encrypt 등), HSTS 등 보안 헤더, TLS 버전·암호 스위트
- [ ] 비밀값은 시크릿 매니저로, 운영 키와 개발 키 분리
- [ ] DB는 외부에서 직접 접속 불가, 최소 권한 계정
- [ ] 클라우드 계정 MFA, IAM 최소 권한
- [ ] 백업 + **복구 테스트**, 백업도 암호화
- [ ] 스테이징 환경 분리 (공격 실습은 스테이징에서)
- [ ] 앱스토어 제출: Apple 개인정보 라벨, Google Play 데이터 보안 섹션 작성

**결과물**: `security/deployment-checklist.md`

## 6단계 — 개인정보·컴플라이언스 (5~6개월)

**목표**: 규정이 개발 요구사항으로 어떻게 바뀌는지 이해한다. **이 로드맵에서 실무 가치가 가장 큰 단계.**

**참고 법령·자료**
- 개인정보 보호법, 「개인정보의 안전성 확보조치 기준」
- 위치정보의 보호 및 이용 등에 관한 법률 (현재 위치를 쓰는 기능이 있을 때)
- 정보통신망법
- (금융 SI 대비, 선택) 전자금융거래법 / 전자금융감독규정 — 2차 정산 기능이 해당되는지도 확인

**할 일**
- [ ] 「개인정보의 안전성 확보조치 기준」부터 읽기 (분량이 적고 개발 요구사항과 가장 직접 연결됨)
- [ ] Travel Copilot이 처리하는 개인정보 목록 작성 (바우처 속 여권번호 = 고유식별정보 여부 포함)
- [ ] 개인정보 처리방침 작성 (앱스토어 제출 전 필수)
- [ ] 국외 이전 고지: Google API, 해외 클라우드로 개인정보가 나가는 경우
- [ ] 위치정보법 적용 여부 확인 (위치기반서비스 사업자 신고 필요한지)
- [ ] 회원 탈퇴 시 파기 범위: DB, 오브젝트 스토리지, 백업, 로그
- [ ] 화면·로그 출력 시 개인정보 마스킹
- [ ] 개인정보 처리 시스템(관리자 기능) 접근 기록 보관, 접근통제
- [ ] **"규정 조항 → 요구사항 → Travel Copilot 구현 위치" 매핑표 작성**

**결과물**: `security/compliance-mapping.md`, 개인정보 처리방침

## 7단계 — 로깅·모니터링·사고 대응 (7~8개월)

**목표**: 문제가 생겼을 때 빨리 알아채고, 무엇을 해야 할지 아는 상태.

- [ ] 감사 로그 설계: 누가 / 언제 / 어떤 데이터를 / 어떤 행위로 (특히 바우처 다운로드, 멤버 추가·삭제, 권한 변경)
- [ ] 로그에 토큰·개인정보가 섞이지 않도록 필터링
- [ ] Loki + Grafana(또는 유사 스택)로 로그 수집·시각화
- [ ] 알림 규칙: 로그인 실패 급증, 리프레시 토큰 재사용 감지, 한 사용자의 대량 조회, Google API 사용량 급증
- [ ] 개인정보 유출 의심 시 대응 절차서 (탐지 → 차단 → 영향 범위 파악 → 신고·통지 → 재발 방지)
- [ ] 최근 국내 보안 사고 사례 2~3건을 "어디서 놓쳤나" 관점으로 정리

**결과물**: 모니터링 대시보드, `security/incident-response.md`

## 8단계 — 2차 기능 보안: LLM · 정산 (9~11개월)

**목표**: 2차 기능(AI 코파일럿, 도슨트, 준비물 체크리스트, 영수증 OCR, 정산)을 만들 때 새로 생기는 위협에 대응한다.

### LLM 기능
**기준 자료**: OWASP Top 10 for LLM Applications
- [ ] OWASP LLM Top 10 각 항목을 내 설계에 대입해 점검
- [ ] 간접 프롬프트 인젝션: Google 장소 리뷰, 영수증 이미지 속 글자, 바우처 내용을 지시문이 아닌 데이터로 취급
- [ ] LLM이 호출하는 도구 권한 최소화 (일정 수정은 사용자 확인 후에만)
- [ ] LLM 비용 남용 방지: 사용자별 호출·토큰 한도
- [ ] 모델에 보내는 데이터 최소화, 개인정보 마스킹
- [ ] 대화 로그 보관·파기 정책

### 정산 (M5)
- [ ] 금액은 float가 아닌 정수(최소 통화 단위) 또는 Decimal
- [ ] 환율 출처·시점 기록, 정산 결과 재계산 가능하게
- [ ] 동시에 지출을 수정·삭제할 때 정산 금액이 어긋나지 않는지 (트랜잭션, 잠금)
- [ ] 다른 멤버의 지출을 수정할 수 있는 권한 규칙 정의

**결과물**: `docs/features/` 아래 LLM 기능 명세 (보안 설계 포함) + 구현
