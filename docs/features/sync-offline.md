## 1. 목적

여행 중에는 데이터가 없거나 느린 곳이 많다. 지금 앱은 서버에 닿지 못하면 여행 목록도 일정도 보여주지 못한다. F6은 **마지막으로 받은 여행 목록과 일정을 기기에 저장해 두고, 오프라인에서도 읽을 수 있게** 한다. 수정은 지금처럼 온라인에서만 한다 (04-architecture D6).

함께 **기기에 남은 데이터를 언제 지우는지**(내보내짐, 여행 삭제, 로그아웃, 계정 전환)를 구현한다. 오프라인 캐시는 편리한 만큼, 내보내진 사람이나 다음 사용자에게 남는 위험이 생기기 때문이다 (T08, T34).

## 2. 사용자 시나리오

1. 사용자가 온라인에서 여행 목록과 여행 상세를 연다. 앱은 받은 내용을 기기 DB에 저장한다
2. 비행기 안에서 앱을 연다. 서버에 닿지 못해도 저장된 목록이 바로 보이고, 위에 "오프라인 · 마지막 동기화: 3시간 전" 배너가 뜬다
3. 여행을 열면 일정(제목·계획 시각·머무는 시간·메모·이동수단)이 보인다. 이동시간 자리에는 "이동시간은 연결 후 표시", 지도 탭에는 "지도는 연결 후 볼 수 있습니다"가 나온다
4. 일정 추가·수정 버튼은 비활성이고, 누르면 "연결 후 수정할 수 있습니다"가 나온다
5. 착륙 후 배너의 [다시 시도]를 누르거나 앱으로 돌아오면 앱이 최신 내용을 받아 화면과 캐시를 바꾼다. 배너가 사라진다
6. 그사이 owner가 이 사람을 여행에서 내보냈다면, 다음 목록 갱신 때 그 여행이 목록과 기기에서 사라진다
7. 로그아웃하면 기기의 여행 캐시가 전부 지워진다. 다른 계정으로 로그인해도 이전 사람의 여행은 보이지 않는다

## 3. 완료 조건

- [ ] 여행 목록과 여행 스냅샷을 기기 DB(drift)에 저장하고, 화면은 캐시를 먼저 그린 뒤 뒤에서 갱신한다
- [ ] 서버를 끈 상태로 앱을 새로 시작해도 로그인 상태가 유지되고, 저장된 목록·일정이 보인다
- [ ] 오프라인 배너(마지막 동기화 시각, [다시 시도]), 수정 버튼 비활성
- [ ] 캐시에 **좌표가 저장되지 않는다** (Google 약관, 05-data-model 2절)
- [ ] 목록에서 사라진 여행, 404가 난 여행, 내가 삭제했거나 나간 여행의 캐시를 지운다
- [ ] 로그아웃하면 DB 파일을 통째로 지우고, 다른 계정으로 로그인하면 이전 계정의 캐시를 지운다
- [ ] 409·403·404 처리가 캐시와 맞게 동작한다 (충돌 뒤 받은 최신 내용으로 캐시가 바뀜)
- [ ] 서버 없이(Mac Wi-Fi 끔 또는 nginx 중지) 시뮬레이터에서 전체 흐름 수동 확인

## 5. 핵심 설계 결정

### 5.1 무엇을 저장하나 — 서버 응답 그대로, 좌표만 빼고

| 저장 | 내용 | 저장 시점 |
|---|---|---|
| 여행 목록 | `GET /trips` 전체 페이지를 받은 결과 | 목록 갱신 성공 시 |
| 여행 스냅샷 | `GET /trips/{id}`: 여행 정보 + 내 역할 + 멤버 + 전체 일정 항목 | 상세 갱신 성공 시, 미리 받기 (5.6) |
| 메타 | 캐시 주인 사용자 ID, 목록 마지막 동기화 시각 | 위와 같이 |

- **좌표(`location`)는 저장 직전에 지운다.** 일정 항목의 `place_id`, 사용자가 쓴 제목·메모·계획 시각·이동수단만 남는다 (`place_id`는 기한 없이 저장 가능)
- 좌표는 지금처럼 **온라인으로 받은 메모리 값**에서만 지도에 쓴다. 캐시에서 그린 화면이면 지도 탭은 오프라인 안내를 보여준다 (캐시에는 좌표가 없어 "장소 없음"으로 잘못 보이는 것을 막는다)
- 서버가 주지 않는 정보(장소 이름·주소·이동시간)는 애초에 스냅샷에 없다

### 5.2 DB 구조 — 응답 JSON을 여행 단위로 통째로

```
cache_meta     (key PK, value)                       -- owner_user_id, trips_synced_at
cached_trips   (trip_id PK, json, position)          -- 목록 한 줄 = Trip JSON
cached_snapshots (trip_id PK, json, synced_at)       -- 스냅샷 JSON (location 제거)
```

- 항목을 컬럼으로 나누지 않고 **JSON 그대로** 저장한다. 앱은 캐시를 조회 조건으로 검색하지 않고, 갱신할 때 통째로 바꾸기 때문이다. 서버 응답 형식이 바뀌어도 DB 마이그레이션이 거의 필요 없다
- 캐시를 읽다가 JSON 해석에 실패하면(앱 업데이트로 형식이 바뀜 등) 그 행을 지우고 캐시가 없는 것처럼 동작한다
- 갱신은 **서버 응답이 성공했을 때만**, 그 응답으로 바꾼다. 수정 요청을 보내면서 캐시를 먼저 고치지 않는다 (서버가 단일 진실 원천, 04-architecture 7절)
- 바우처는 F7에서 `cached_snapshots.json`에 들어오는 바우처 목록과 별도 파일 저장소로 붙인다

### 5.3 "캐시 먼저, 온라인이면 갱신" — repository가 담당

```
화면 열기 → repository.watch(trip)
  1) 캐시 있으면 즉시 내보냄 (source: cache, syncedAt)
  2) 서버 요청
     성공 → 캐시 덮어쓰기 → 내보냄 (source: server, location 포함 원본)
     NetworkException → 캐시 유지, 상태 offline
     404 → 그 여행 캐시 삭제 → "접근할 수 없는 여행" → S03
     403 → 스냅샷 다시 받기 (역할이 바뀌었을 수 있음)
  3) 캐시도 없고 실패 → 지금처럼 오류 화면 + [다시 시도]
```

- 화면은 `Synced<T>`(데이터, 출처 cache/server, 마지막 동기화 시각, 갱신 중 여부)를 받는다. 위젯은 drift·dio를 직접 부르지 않는다 (08-conventions)
- 지금의 `tripListProvider`·`tripSnapshotProvider`를 이 repository 위로 옮긴다. 수정 성공 뒤 `invalidate`하는 기존 흐름은 그대로 두면 다시 받은 결과가 캐시에 써진다

### 5.4 온라인·오프라인 판단 — 실제 요청 결과로

- **별도 패키지(connectivity_plus 등)를 쓰지 않는다.** Wi-Fi에 붙어 있어도 서버에 못 닿는 경우(기내 Wi-Fi 로그인 전, 서버 장애)가 많아서, "네트워크 연결됨"은 믿을 수 없다
- dio 인터셉터가 응답을 받으면 `online`, `NetworkException`이면 `offline`으로 앱 전체 상태(`connectionStatusProvider`)를 바꾼다. 서버가 에러(4xx·5xx)를 보낸 것도 "닿았다"이므로 online
- 다시 확인하는 때: 배너의 [다시 시도], 당겨서 새로고침, **앱이 다시 앞으로 올 때**(AppLifecycle resumed). 몰래 주기적으로 재시도하지 않는다
- 시작 직후(상태 unknown)에는 버튼을 막지 않는다. 시작하면 바로 갱신을 시도하므로 곧 상태가 정해진다

### 5.5 오프라인일 때 막는 것

| 화면 | 오프라인 동작 |
|---|---|
| S03 여행 목록 | 배너, [여행 만들기]·[링크로 참여] 비활성 |
| S05 여행 상세 | 배너, 여행 수정·삭제·나가기 비활성. 멤버 탭의 역할 변경·내보내기·소유권 이전·[초대 링크] 비활성 |
| S06 일정 | [추가]·수정·삭제·순서 변경 비활성. 이동 구간 자리에 "이동시간은 연결 후 표시" |
| S07 지도 | "지도는 연결 후 볼 수 있습니다" (캐시에서 그린 화면이면 항상) |
| 장소 시트 | "장소 정보는 연결 후 볼 수 있습니다" + 사용자가 쓴 제목·메모 |
| S15·S16 초대 | 온라인 전용. 오프라인이면 오류 문구 (F5 그대로) |

비활성 버튼을 누르면 "연결 후 수정할 수 있습니다"를 보여준다. 그래도 요청이 나갔다가 실패하면 지금처럼 "저장되지 않았습니다"를 보여주고 몰래 재시도하지 않는다 (07-screens 5절).

### 5.6 어떤 여행을 미리 받아 두나

- 연 적 있는 여행은 열 때마다 저장된다
- 그런데 오프라인이 되는 날 처음 여는 여행이면 캐시가 없다. 그래서 **목록 갱신이 성공하면, 끝나지 않은 여행(`end_date >= 오늘`)의 스냅샷을 뒤에서 받아 둔다** (최대 10개, 동시 2개, 시작일이 가까운 순)
- 미리 받기는 실패해도 화면에 알리지 않는다. 로그에는 결과 코드만 남긴다
- 스냅샷 요청은 Google API를 부르지 않으므로 비용이 없다

### 5.7 기기 데이터 정리 (T08, T34)

| 시점 | 지우는 것 | 방법 |
|---|---|---|
| 목록 갱신 성공 시 목록에 없는 여행 (내보내짐·삭제됨) | 그 여행의 목록 행·스냅샷 | 행 삭제 |
| 여행 요청에서 404 | 그 여행의 목록 행·스냅샷 | 행 삭제 |
| 내가 여행을 삭제했거나 나감 (성공 응답) | 그 여행의 목록 행·스냅샷 | 행 삭제 |
| 로그아웃 (온라인·오프라인 모두) | **DB 전체** | DB를 닫고 파일 삭제 (`-wal`·`-shm` 포함) |
| 다른 계정으로 로그인 (`owner_user_id`와 다름) | DB 전체 | 위와 같음 |
| 토큰 갱신 최종 실패 → 로그인 화면 | 지우지 않음 | 같은 계정으로 다시 로그인하면 이어서 쓴다 (07-screens 5절) |

- **목록에 없는 여행은 전체 페이지를 다 받았을 때만 지운다.** 첫 페이지만 받고 나머지가 실패했는데 지우면, 멀쩡한 여행 캐시가 사라진다
- **SQLite는 행을 지워도 내용이 파일의 빈 공간에 남는다.** 그래서 `PRAGMA secure_delete = ON`으로 지운 자리를 0으로 덮고, 전체 삭제는 행 삭제가 아니라 파일 삭제로 한다
- 캐시 주인 확인: 로그인에 성공하면 그 사용자 ID와 `owner_user_id`를 비교해서, 다르면 DB 전체를 지운 뒤 새로 시작한다. 앱 시작 시 저장된 사용자와 DB 주인이 다를 때도 같다
- 내보내진 사람이 계속 오프라인이면 기기의 캐시를 지울 방법이 없다. 이미 "수용하는 위험"으로 기록되어 있다 (threat-model 5절). 내보내기 확인 대화상자에 이 점을 안내한다 (07-screens S14)

### 5.8 DB 파일 위치와 백업

- **앱 지원 폴더(iOS `Library/Application Support`, Android 앱 전용 `files`)**에 둔다. iOS `Documents`는 설정에 따라 파일 앱에서 보일 수 있어서 쓰지 않는다
- 기기 백업에서 제외 (T19): Android는 `allowBackup="false"`와 데이터 추출 규칙, iOS는 DB 폴더에 백업 제외 속성(`isExcludedFromBackup`)을 단다. iOS는 Dart API가 없어서 짧은 네이티브 코드가 필요하다 (12절 열린 질문 3)
- DB 자체 암호화(SQLCipher)는 하지 않는다 (12절 열린 질문 2). 앱 전용 폴더는 다른 앱이 읽을 수 없고, iOS·Android 모두 기기 잠금과 연결된 파일 암호화가 기본으로 켜져 있다. 일정 메모에 민감한 내용이 들어갈 수 있다는 점은 위험으로 기록한다

### 5.9 로그에 남기지 않는 것

캐시 내용(여행 제목·메모·멤버 이름)은 로그에 남기지 않는다. 캐시 동작 로그는 "캐시 적중/갱신 성공/결과 코드/지운 여행 수"까지만 남긴다.

## 6. API

**서버 변경 없음.** 쓰는 API:

| 메서드 | 경로 | 앱에서의 쓰임 |
|---|---|---|
| GET | `/trips` | 목록 갱신. 모든 페이지를 받은 뒤 캐시 교체·사라진 여행 삭제 |
| GET | `/trips/{trip_id}` | 스냅샷 갱신·미리 받기. 응답의 `location`은 캐시에 쓰기 전에 제거 |
| GET | `/trips/{trip_id}/days/{date}` | 이동 구간 (온라인 전용, 캐시하지 않음 — F4 그대로) |

모든 응답의 `Cache-Control: no-store`는 그대로 둔다. 이것은 HTTP 캐시(프록시·dio 캐시)를 막는 것이고, 앱이 직접 관리하는 DB와는 별개다. 앱 DB는 이 문서의 규칙(좌표 제외, 정리 시점)으로 관리한다.

## 7. 데이터 변경

- 앱 로컬 DB(신규, drift): 5.2절의 테이블 3개. 스키마 버전 1

## 8. 보안 요구사항

| 위협 | 요구사항 | 확인 방법 |
|---|---|---|
| T08 내보낸 멤버의 계속 접근 | 목록에서 사라진 여행·404 여행의 캐시 삭제. 전체 페이지를 받은 경우에만 | 단위: `list_refresh_removes_missing_trips`, `partial_list_failure_keeps_cache`, `not_found_removes_trip_cache` |
| T34 (신규) 계정 전환 시 이전 사용자 캐시 노출 | 로그아웃 시 DB 파일 삭제, 다른 계정 로그인 시 전체 삭제 | 단위: `logout_deletes_db_files`, `other_account_login_wipes_cache`, `same_account_relogin_keeps_cache` |
| T34 지운 데이터가 파일에 남음 | `secure_delete` 켬, 전체 삭제는 파일 삭제 | 단위: `secure_delete_enabled`, 삭제 후 DB 파일 바이트에 지운 여행 제목이 없는지 검사 |
| Google 약관 (05-data-model 2절) | 캐시에 좌표 없음 | 단위: `cached_snapshot_has_no_location` (저장된 JSON에 `location`·위경도 없음) |
| T19 백업 유출 (일부) | DB는 앱 지원 폴더, 백업 제외 | 단위: DB 경로가 Documents가 아님. Android 매니페스트 검사 테스트 (F5 `deep_link_config_test` 방식) |
| T29 동시 수정 | 409 뒤 받은 최신 내용으로 캐시가 바뀜. 캐시를 먼저 고치지 않음 | 위젯: 충돌 → 새로고침 → 캐시 갱신 |
| 로그 노출 | 캐시 내용을 로그에 남기지 않음 | 단위: 캐시 동작 중 로그에 제목·메모 문자열이 없음 |

**방어 제거 시험** (F5와 같은 방식, 구현 후 원복):
1. 좌표 제거 코드를 빼면 → `cached_snapshot_has_no_location` 실패
2. "전체 페이지 받았을 때만 삭제" 조건을 빼면 → `partial_list_failure_keeps_cache` 실패
3. 로그인 시 주인 확인을 빼면 → `other_account_login_wipes_cache` 실패
4. `secure_delete`를 빼면 → 파일 바이트 검사 실패

## 10. 테스트 계획

- 서버: 변경 없음. 기존 361개가 그대로 통과하는지만 확인
- 앱 단위 (메모리 DB + 가짜 API)
  - 캐시 먼저 내보내고 서버 응답으로 교체 / 네트워크 실패 시 캐시 유지 + offline / 캐시도 없으면 오류
  - 8절 보안 테스트 전부
  - JSON 해석 실패 행은 지우고 캐시 없음으로 동작
  - 미리 받기: 끝나지 않은 여행만, 최대 10개
- 앱 위젯
  - 오프라인 배너와 마지막 동기화 문구, [다시 시도]
  - 오프라인일 때 S03·S05·S06 수정 버튼 비활성, 지도 탭 오프라인 문구
  - 404 → 목록으로 이동하고 캐시 삭제
- 수동 확인 (00 가이드에 50번부터 추가)
  1. 온라인에서 여행 두 개를 열어 본다
  2. Mac Wi-Fi를 끄거나 `docker compose stop nginx` → 앱을 완전히 종료 후 다시 실행 → 목록·일정이 보이고 배너가 뜨는지
  3. 수정 버튼 비활성, 지도 탭 안내 문구
  4. 서버를 다시 켜고 [다시 시도] → 배너가 사라지고 최신 내용
  5. 두 번째 계정에서 첫 계정을 여행에서 내보냄 → 첫 계정에서 목록 새로고침 → 여행이 사라지고, 다시 오프라인으로 해도 보이지 않음
  6. 로그아웃 → 다른 계정 로그인 → 이전 여행이 보이지 않음
  - 실기기 비행기 모드 확인은 P1(실기기 설치) 후, Android는 F1~F6을 한 번에

## 12. 열린 질문

1. **미리 받기 범위**: 끝나지 않은 여행의 스냅샷을 목록 갱신 때 자동으로 받아 둘까? → **제안: 받는다** (최대 10개). 오프라인이 되는 날 처음 여는 여행도 볼 수 있게 하기 위해서다. 받지 않으면 "한 번이라도 열어 본 여행만" 오프라인에서 보인다
2. **DB 암호화(SQLCipher)**: → **제안: MVP에서는 하지 않는다.** OS의 앱 격리와 기본 파일 암호화에 맡기고, 위험을 위협 모델에 기록한다. 바우처(F8)는 내용이 더 민감해서 계획대로 따로 AES-GCM으로 암호화한다. 앱 잠금(2차)을 넣을 때 다시 검토한다
3. **백업 제외를 지금 할까**: → **제안: F6에서 한다.** 기기에 데이터가 처음 쌓이는 기능이 F6이라서다. F8은 같은 방식을 바우처 폴더에 그대로 쓴다
4. **네트워크가 돌아온 것을 자동으로 알아챌까**(connectivity_plus): → **제안: 쓰지 않는다.** 5.4절 이유. [다시 시도], 당겨서 새로고침, 앱 복귀로 충분한지 써 보고 판단한다

## 13. 결정 사항 (2026-11-15 승인, 제안대로)

1. 끝나지 않은 여행의 스냅샷을 목록 갱신 때 미리 받는다 (최대 10개, 동시 2개)
2. MVP에서 DB 암호화(SQLCipher)는 하지 않는다. 위협 모델 "수용하는 위험"에 기록
3. 기기 백업 제외는 F6에서 한다 (Android 백업 끄기, iOS DB 폴더 제외 속성)
4. connectivity_plus는 쓰지 않는다

**방어 제거 시험** (하나씩 빼고 테스트 실행 후 원복, 원본과 바이트 비교로 원복 확인)

| 뺀 방어 | 실패한 테스트 |
|---|---|
| 저장 전 좌표 제거 | `cached_snapshot_has_no_location`, 저장소 테스트 "캐시에는 좌표 없이 저장" |
| 목록을 다 받은 뒤에만 교체 (받기 전에 먼저 지우게 바꿈) | `partial_list_failure_keeps_cache` |

| `PRAGMA secure_delete` | `secure_delete_enabled`, **지운 여행 제목이 DB 파일 바이트에 남음** (설정이 없으면 행을 지워도 내용이 파일에 남는다는 것을 확인) |

**명세와 달라진 점**
- 오프라인일 때 수정 버튼을 흐리게(비활성) 만들지 않고, 누르면 "연결 후 수정할 수 있습니다"를 보여주고 막는다. 비활성 버튼은 눌러도 반응이 없어 이유를 알 수 없기 때문이다. 화면별 범위는 5.5절 그대로
- 장소 시트의 오프라인 안내에는 일정 제목만 보인다 (메모는 일정 화면에서 보인다)
- 409 충돌 대화상자는 F2·F3에서 만든 것을 그대로 쓴다. 충돌 뒤 무효화로 다시 받은 결과가 캐시에 써진다
