## 4. 2단계 — 기능마다 반복하는 순서

| # | 단계 | 담당 | 내용 |
|---|---|---|---|
| ① | 명세 | Claude | `docs/features/<기능>.md` — 시나리오, 완료 조건, API·데이터 변경, 권한 규칙, 관련 위협 ID와 보안 요구사항 |
| ② | 명세 승인 | 나 | 승인 전에는 코드를 쓰지 않는다 |
| ③ | 구현 | Claude | `feat/<기능>` 브랜치. 서버: 마이그레이션 → 모델·스키마 → 서비스 → API → 테스트 / 앱: 데이터 → 상태 → 화면 |
| ④ | 검증 | Claude | 테스트·lint 통과, 로컬에서 실제 실행해 시나리오 확인. 실패는 실패로 보고 |
| ⑤ | 보안 점검 | security/ 에이전트 | 결과를 `security/reviews/YYYY-MM-DD-<기능>.md`에 기록 |
| ⑥ | 반영 | Claude | 점검 결과 수정, 위협 모델 상태·로드맵 체크박스·명세 갱신 |
| ⑦ | 변경 승인·커밋 | 나 → Claude | 내가 변경 내용을 확인하고 커밋을 승인하면, Claude가 커밋하고 push·PR 생성 명령어와 PR 본문(변경 요약, 테스트 결과, 점검 결과 링크)을 전달 |
| ⑧ | push·PR·머지 | 나 | 명령어 실행, CI 통과 확인, 리뷰 후 main에 squash 머지 |

**명세와 구현이 달라져야 할 때**: 코드를 먼저 바꾸지 않는다. 명세를 고쳐서 승인받은 뒤 구현한다.

## 5. git 규칙

- **커밋은 내 승인 후에만** Claude가 한다. 브랜치 생성·전환, 변경 확인은 Claude가 해도 된다. GitHub 작업(push, PR, 머지, 저장소 설정)은 내가 직접 실행하고, Claude는 명령어를 준비해서 전달한다
- `main`은 항상 동작하는 상태. 직접 커밋하지 않는다 (초기 세팅 커밋 제외)
- 브랜치: `feat/<기능>`, `fix/<내용>`, `docs/<내용>`, `chore/<내용>`
- 커밋 메시지: Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`)
- PR 하나 = 기능 하나. 너무 커지면 나눈다
- 머지: squash 머지, 머지 후 브랜치 삭제
- `main` 브랜치 보호: PR 필수, CI 통과 필수

## 6. 완료 기준 (Definition of Done)

- [ ] 명세의 완료 조건을 모두 만족
- [ ] 테스트·lint 통과 (권한 없는 사용자 거절 테스트 포함)
- [ ] 로컬에서 실제 실행해 확인
- [ ] 보안 점검 완료, "높음" 결과는 수정 또는 수용 사유 기록
- [ ] 관련 문서 갱신 (명세, 위협 모델, 로드맵)
- [ ] CI 통과, 리뷰 승인
